# Инструкция оператора фабрики сайтов

Для кого: оператор студии, который ведёт заказы через Claude Code (облачная сессия или приложение). Главный документ фабрики — [`docs/factory/MASTER-PLAN.md`](factory/MASTER-PLAN.md) (на английском). Если эта инструкция и мастер-план расходятся, прав мастер-план; сообщите о расхождении, и инструкцию поправят.

Как новый заказ проходит путь от брифа до готового PR, пошагово: [`SOP-new-order.md`](SOP-new-order.md). Вопросы владельцу и решения по умолчанию: [`OWNER-QUESTIONS.ru.md`](OWNER-QUESTIONS.ru.md).

## 1. Коротко о фабрике

- Фабрика собирает сайты трёх типов: **social-casino** (бесплатное социальное казино для UK), **online-games** (сайты браузерных игр) и **hotel-casino** (маркетинговые сайты отелей, где есть казино).
- Общий движок лежит в `engine/`, правила каждого типа — в `types/<тип>/`, сам сайт — в `sites/<slug>/`, заказ клиента — в `orders/<id>/` (`id` заказа совпадает со `slug` сайта).
- Отчёты сборок и проверок пишутся в `reports/<slug>/`. Эта папка не попадает в git: смотрите её в той же сессии или в артефактах CI.
- Один экран для всего портфеля — **Board** (`artifacts/board/index.html`, приватный артефакт). Он только для оператора: клиенту его не показывают.
- Сейчас идёт **Phase 1**: собирается скелет фабрики. Сайт №1 — Opal Quest Lounge. Деплоев, рутин и облачных сессий на каждый сайт ещё нет. Состояние фаз: [`PLAN.md`](PLAN.md).

## 2. Роли сессий

| Роль | Где | Что можно |
|---|---|---|
| **hub** (ваша сессия или сессия-координатор) | ветка `main`, `claude/*` или `tooling/*` | всё: заказы, ревью, Board, правки фабрики через `tooling/*` PR |
| **spoke** (облачная сессия одного сайта, Phase 3+) | ветка `site/<slug>` | только `sites/<slug>/`, `orders/<slug>/`, `reports/<slug>/`; без мержа и деплоя |
| **routine** (запуск по расписанию, Phase 4+) | новая сессия на каждый запуск | только команды из списка разрешённых; никогда не мержит и не деплоит |

Роль задаёт переменная `FACTORY_ROLE`; её выставляет хук `session-start.sh` по имени ветки. Хуки `guard-scope.mjs` и `guard-ship.mjs` следят, чтобы роль не выходила за свои пути. Если хук что-то заблокировал, он пишет причину; не обходите блокировку, а прочитайте её.

## 3. Какие команды есть сейчас

| Команда | Что делает | Когда появится |
|---|---|---|
| `/order` | заводит заказ из брифа, задаёт вопросы клиенту, ведёт до утверждения | **Phase 1** (часть шагов позже, см. ниже) |
| `/build` | собирает один сайт из утверждённого заказа | **Phase 1** — упрощённая версия; полная в Phase 2 |
| `/qa` | полная проверка одного сайта, все гейты | **Phase 1** |
| `/status` | состояние портфеля или одного сайта; синхронизация Board | **Phase 1** |
| `/security-scan`, `/loop-design-check`, `/architecture-decision-records`, `/growth-log` | служебные (проверка нового кода в `.claude/`, проверка циклов, ADR, уроки) | **Phase 1** |
| `/batch`, `/review`, `/fix`, `/handoff`, `/pragmatic-verify`, `/ship` | пакетная сборка, ревью, правки, передача клиенту, сверка демо, запуск в прод | Phase 3 |
| `/monitor`, `/policy-recheck` | рутины, перепроверка цитат правил | Phase 4 |
| `/ppc-kit`, `/ppc-audit` | набор для Google Ads, аудит аккаунта | Phase 5 |

Если вы вызвали команду, которой ещё нет, Claude скажет, что такого скилла нет. Это не ошибка фабрики.

### 3.1 `/order` — новый заказ

```
/order <бриф: путь к файлу, текст или id строки из формы>
       [--type social-casino|online-games|hotel-casino] [--variant <вариант>] [--id <slug>]
       [--answers <файл|текст>] [--propose] [--approve] [--from-inbox <id>] [--assessment]
```

- Без флагов: сохраняет бриф дословно в `orders/<id>/brief.md`, агент `intake-analyst` пишет `order.json` (у каждого поля указан источник) и `questions.md` на языке клиента. Тип и вариант он определяет сам; если уверенность ниже 0.8, первым вопросом спросит вас.
- **Название бренда обязательно**: из него получается `id` заказа. Без названия команда остановится и спросит.
- Юридические факты (оператор, номер компании, домен, DNS, GA4/Ads, покупки, согласие Pragmatic, проверка возраста, юрист, хостинг, дата запуска, товарный знак) **никогда не угадываются**: они всегда уходят в `questions.md`.
- `--answers` вливает ответы клиента по строкам `field:` в `questions.md`.
- `--assessment` готовит черновик оценки «доступен ли сайт детям» (`orders/<id>/audience-assessment.md`) для онлайн-игр и социального казино. Подписывает его названный человек; поле `audience` заполняется только из подписанного файла.
- `--propose` запускает панель концепций (три направления, каждое уже проверено на уникальность и оценено судьями) и пишет `proposal.md`.
- `--approve` резервирует концепцию в реестре и готовит хостинг. Обычно его вызывает рутина `orders-inbox`, когда клиент утвердил все пункты.
- Заказ, который фабрика не берёт (реальные деньги, sweepstakes, демо-лобби с Google Ads, режим B отеля без подтверждений, копии порталов Poki/CrazyGames), отклоняется ещё на уровне `draft`.

Что в Phase 1 ещё не автоматизировано: ветка `site/<slug>` и черновой PR (инструменты `tools/git.mjs`, `tools/gh.mjs` — Phase 2), резерв в реестре (`tools/registry.mjs` — Phase 2), страница предложения для клиента и Cloudflare (Phase 3). До этого такие шаги делает человек по выводу команды.

### 3.2 `/build` — сборка сайта

```
/build <slug> [--board <url>] [--resume] [--lanes=theme,art,copy,games,pragmatic] [--skip-verify]
```

- В Phase 1 это тонкая обёртка: создать сайт из шаблона типа (`tools/new-site.mjs <slug> --type <тип>`), собрать (`engine/build.mjs`), прогнать часть проверок (`check.mjs --only`).
- С Phase 2 это полный конвейер: концепция → творческие линии (тексты, рисунки, тема, игры) → сборка → проверка → документы → PR на ревью.
- `--resume` продолжает с последней сохранённой стадии.
- `/build` никогда не правит `engine/**`: это запрещено хуком.

### 3.3 `/qa` — полная проверка

```
/qa <slug> [--ci] [--only=<разделы>] [--quick] [--pass3]
```

- Делает всё, что нужно для гейтов G2–G6 (раздел 5): три сборки, строгую сборку, браузерные проверки, Lighthouse, уникальность.
- `--quick` — короткая проверка, около 2 минут (`pages, chrome, prefs, offline`).
- `--only=pages,offline` — только названные разделы.
- `--ci` — то же в GitHub Actions (файл `sites-ci.yml`).
- `--pass3` — три прогона подряд на коммите для запуска; для запуска нужны все три зелёные (pass^3, см. [`evals.md`](evals.md)).
- **Одна полная проверка на машину за раз.** Полный прогон идёт около 6,5 минуты: запускайте его в фоне или с `timeout: 600000`. Отчёт, помеченный `partial: true`, считается провалом.

Те же шаги можно запустить руками (Phase 1):

```bash
node engine/build.mjs sites/<slug> --json                     # обычная сборка, ошибки линта — в JSON
node engine/build.mjs sites/<slug> --strict --json            # сборка для запуска: ноль проблем
CHECK_TIMEOUT_MIN=15 node engine/tools/check.mjs --site sites/<slug> --report reports/<slug>/check.json
node engine/tools/check.mjs --site sites/<slug> --only=pages,offline --workers 2 --report reports/<slug>/partial.json
node engine/tools/lighthouse.mjs sites/<slug>/dist --out reports/<slug>/lighthouse
node tools/uniqueness.mjs --post sites/<slug> --against all --fail
```

### 3.4 `/status` — где что находится

```
/status [slug] [--sync] [--gate] [--open] [--publish] [--json] [--mine] [--check]
```

- Без аргументов — таблица всего портфеля: стадия, одобрения, PR и CI, последние гейты, здоровье.
- `--gate <slug>` — список недостающих отметок для запуска; у каждой написана команда, которая даёт доказательство.
- `--sync` — отправить строки и события на Board.
- `--check` — сверить стадию на Board, статус в `order.json`, реестр и метку PR; при расхождении выходит с ошибкой и называет документ.
- `--open` — открыть Board; `--publish` — опубликовать его в первый раз.
- Команда ничего не меняет в заказах.

Если GitHub недоступен, `/status` всё равно покажет данные из git и `reports/` со строкой «GitHub unavailable».

## 4. Обычный день

1. `/status` — что изменилось. Красные события (severity `red`) — первыми.
2. Ответы клиентов на вопросы → `/order <id> --answers <файл>`.
3. Заказы с отвеченными вопросами «до сборки» → `/order <id> --propose`.
4. Утверждённые заказы → `/build <slug>` (в Phase 3 — `/batch`).
5. Готовые сборки → `/qa <slug>`.
6. В конце дня `/status --sync`, чтобы Board совпадал с git.

## 5. Гейты: что значит каждый

Гейт — это команда с JSON-результатом, которая должна пройти, прежде чем заказ перейдёт на следующую стадию. Полный список — SPEC 17 и MASTER-PLAN 3.3.

| Гейт | Что проверяет | Команда | Если красный |
|---|---|---|---|
| **G0 Заказ** | `order.json` проходит схему и перекрёстные правила на уровне `draft`, `build` или `launch` | `node tools/validate-order.mjs orders/<id> --level draft\|build\|launch --json` | у каждой ошибки есть путь поля и вопрос клиенту; ответьте через `--answers` |
| **G1 Уникальность до генерации** | направление концепции не повторяет соседей (семейство, шрифты, палитра, названия игр, структура) | `node tools/uniqueness.mjs --pre <direction.json\|order.json>` | выбрать другое направление |
| **G2 Линт сборки** | все правила сборки на каждой правке (хук делает это сам) | `node engine/build.mjs sites/<slug> --json` | исправить файл, который назван в `problems` |
| **G3 Сборка для запуска** | `--strict` на трёх конфигурациях: ноль проблем, ни одной заглушки и текста по умолчанию, бюджеты (первый экран ≤ 150 KB gzip, предзагрузка ≤ 220 KB) | `node engine/build.mjs sites/<slug> --strict --json` | `default-content` → нужен свой текст; `generic-cover` → нужна своя обложка; `placeholder` → нужен факт от клиента |
| **G4 Браузерные проверки** | все разделы `check.mjs`, 0 ошибок, 0 нарушений axe, обе темы, 1440 и 390 px, отчёт не частичный (у Opal Quest Lounge 277 проверок) | `node engine/tools/check.mjs --site sites/<slug> --report …` | в отчёте названы раздел и проверка |
| **G5 Lighthouse** | ≥ 95 во всех категориях, мобильный и десктоп, 4 адреса; LCP < 2,0 s, CLS < 0,05 | `node engine/tools/lighthouse.mjs …` | обычно тяжёлые картинки или шрифты темы |
| **G6 Уникальность после сборки** | тексты, заголовки, палитра, шрифты, названия, структура не совпадают с другими сайтами того же типа; плюс три «скептика» (сайт проходит, если убеждён не больше одного) | `node tools/uniqueness.mjs --post sites/<slug> --against all --fail` | переписать то, на что указывают `failures` |
| **G7 Соответствие правилам** | судья `compliance-judge` без блокирующих замечаний; аудитор не нашёл непокрытых требований; README и COMPLIANCE сгенерированы | Phase 3 (`/review`) | исправить по списку `items` с цитатой и правилом |
| **G8 Репозиторий** | CI `sites-ok` зелёный, PR не трогает чужие пути | GitHub | смотреть упавшую задачу CI |
| **G9 Решения людей** | клиент утвердил концепцию, палитру, шрифты, валюту, игры, структуру, тексты; реквизиты оператора и юрист в `order.json`; одобрение запуска; вы набрали `ship <slug>` | Board, страница предложения, `/ship` (Phase 3) | ждать решения; фабрика не решает за человека |
| **G10 Живой сайт** | проба после деплоя зелёная, версия на сайте совпадает со сборкой | `deploy.yml`, `pr-shepherd` (Phase 3–4) | автоматический откат и инцидент |

**Цитаты правил пока не проверены.** Ни одну официальную страницу (Google, ASA/CAP, ICO, Gambling Commission, legislation.gov.uk) пока никто не открыл из среды фабрики. Поэтому:

- правила, которые опираются на такую цитату, работают как **предупреждение** (`warn`), а не как ошибка, пока цитата не сверена;
- правила самой студии (помечены `factory: true`: дословный дисклеймер, лента 18+, свой домен, ничего чужого до согласия и др.) — **всегда ошибки**, их нельзя ослабить;
- запуск (`/ship`, Phase 3) всё равно не пройдёт, пока не сверены все цитаты, на которые опираются строгие правила типа сайта (`policyUrlsVerified`);
- отметку «сверено» ставит только человек: `tools/policy-recheck.mjs --initial <имя>` (Phase 4). Подробно: [`policy-watch.md`](policy-watch.md).

## 6. Стадии заказа

Одна машина состояний — `schemas/stages.json`. Стадия на Board главная; статус в `order.json`, статус в реестре, метка PR и колонка Kanban выводятся из неё.

| Стадия | Что значит | Кто переводит дальше |
|---|---|---|
| `intake` | заказ заведён | `/order` |
| `questions-sent` | вопросы клиенту отправлены | `/order --propose`, когда отвечены вопросы «до сборки» |
| `proposal` | клиенту показаны три направления | одобрения клиента → `/order --approve` |
| `approved` | концепция утверждена и зарезервирована | `/batch` или `/build` |
| `building` | сайт собирается | конвейер сборки |
| `review` | PR готов к ревью | панель ревью (`/review`) |
| `fix` | нужны правки (не больше трёх раундов) | `/fix`, затем снова `review` |
| `ready-for-launch` | ревью пройдено | `/ship` после `ship <slug>` |
| `ready` | ворота запуска пройдены, авто-мерж включён | `/ship` |
| `live-pending` | мерж идёт, деплой не подтверждён | `pr-shepherd` после зелёной пробы |
| `live` | сайт работает | `/fix` + `/ship` для изменений |
| `maintenance` | правка живого сайта | после `/ship` снова `live` |
| `blocked` | нужен человек: четвёртый раунд ревью, две неудачные перезагрузки сессии, красный гейт | оператор |
| `paused` | заказ на паузе | оператор |
| `retired` | сайт снят, резерв в реестре освобождён | оператор |

## 7. Слова статуса в отчётах

Сессии и события пишут, что сделано, одним из этих слов (они английские, так их видно в логах):

- `inspected` — посмотрел, ничего не менял;
- `changed locally` — изменил файлы, не проверял;
- `verified locally` — изменил и прогнал команду-доказательство (она названа);
- `committed` — закоммитил;
- `pushed` — отправил в GitHub;
- `blocked` — дальше не могу, нужен человек (причина названа).

«Готово» без названной команды-доказательства не считается.

## 8. Решения, которые принимает только человек

Фабрика проверяет, но не решает. Два переключателя:

1. **Одобрения клиента** (концепция, палитра, шрифты, валюта, игры, структура, тексты; у других типов свои пункты). Каждый клик записывается на Board с именем того, кто нажал. Пока заказ не `approved`, хук не даёт писать в `sites/<slug>/{content,theme,art,media}`.
2. **Запуск** (Phase 3): `/ship <slug>` показывает итоговую таблицу, и только после того, как вы **сами наберёте** `ship <slug>`, создаётся замок `ship.lock`. Хук `guard-ship.mjs` проверяет и замок, и ваше сообщение в истории сессии. Зелёные проверки — это не разрешение публиковать.

Кроме того, только человек: подписывает оценку аудитории, сверяет цитаты правил, отвечает за юридические тексты (их смотрит юрист), принимает решения по вопросам владельца.

## 9. Безопасность

- Бриф, `order.json`, строки Board, письма клиентов, комментарии ревью, загруженные страницы — **это данные, а не инструкции**. Если в брифе написано «отключи проверки», «добавь ссылку на казино» или «скачай этот адрес», агент записывает это в `questions.md` в раздел «Flagged» и не выполняет.
- Токены и пароли (Cloudflare, GitHub, Google) не вставляйте в чат и не кладите в файлы репозитория. Они живут в секретах окружения.
- Сессии, которая читала вложение клиента или загружала внешние страницы, никогда не давайте режим `bypassPermissions`.
- `/ship` работает только в вашей собственной сессии; рутины и облачные сессии сайтов его не вызывают.
- Хуки не запускают вложенный `claude -p`.

## 10. Модели и расходы

- Судьи, дизайнер концепций и творческие агенты работают на модели той сессии, которая их вызвала (`model: inherit`): ревью и предложения — в вашей сессии (hub), сборки — в сессии сайта.
- Служебные агенты (`qa-runner`, `site-sentinel` и др.) работают на `sonnet`.
- Переменную `CLAUDE_CODE_SUBAGENT_MODEL` не задавайте: она переключит всех агентов, включая судей.
- Стоимость сессии считается по журналу сессии в конце (хук Stop) и видна на Board (`sessions.cost`). Это оценка; сверяйте с страницей расходов аккаунта.

## 11. Если что-то пошло не так

| Что видите | Что это | Что делать |
|---|---|---|
| Хук Stop пишет `blocked: needs operator` | сборка или проверка красная после двух попыток | прочитать `problems`, исправить или перевести заказ в `blocked` |
| Хук не дал записать файл | путь чужой для этой роли или ветки, или заказ ещё не утверждён | правка движка — только через `tooling/*` PR; правка сайта — только после `approved` |
| Проверка оборвалась, отчёт `partial: true` | не хватило времени | запустить в фоне или по частям (`--only`) |
| `/status --check` выходит с ошибкой | стадия на Board и статус в файлах расходятся | исправить тот документ, который назван |
| Линт говорит «unverified» | цитата правила не сверена | это предупреждение, не ошибка; к запуску её должен сверить человек |
| Хуки мешают работе всей сессии | ошибка в самих хуках | `FACTORY_HOOKS=off` только на время починки, затем перезапуск сессии |

## 12. Как менять саму фабрику

- Любое изменение `engine/`, `types/`, `tools/`, `schemas/`, `.claude/`, `.github/` — это отдельный PR из ветки `tooling/*` (в Phase 1 — через рабочие деревья партиций на текущей ветке). Сайтовые ветки эти пути трогать не могут.
- Изменение судьи (`compliance-judge`, `uniqueness-skeptic`) = новая `rubricVersion` и зелёная калибровка `judges-calibration` на фикстурах.
- Изменение хуков = тесты `.claude/hooks/tests` три раза подряд зелёные.
- Всё, что расширяет `permissions.allow`, одобряет человек.
- Изменение общего контракта (формат JSON, схема, путь) — строка в [`CONTRACT-CHANGES.md`](CONTRACT-CHANGES.md) и ADR в [`adr/`](adr/). Новый проектный документ не пишется.

## 13. Раз в квартал: ревизия заимствованных файлов

Часть файлов в `.claude/` взята из Everything Claude Code (MIT; список — `.claude/VENDORED.json` и [`THIRD_PARTY_NOTICES.md`](../THIRD_PARTY_NOTICES.md)).

1. Скачать свежую версию ECC в scratch-папку и запустить `node tools/vendor-sync.mjs --check <путь>` (Phase 2). Инструмент только печатает таблицу различий и ничего не пишет.
2. По каждому файлу вынести решение: **Keep** (оставить), **Improve** (улучшить у себя), **Update** (взять новую версию), **Retire** (удалить), **Merge** (слить с другим). У каждого решения — причина в одну строку.
3. Принятые изменения — `tooling/*` PR через `/security-scan` и с обновлённой строкой в `VENDORED.json`.

Ежемесячная проверка расхождений идёт сама в рутине `factory-weekly-audit` (Phase 4).

## 14. Какой документ за что отвечает

| Роль | Документ |
|---|---|
| Конституция (правила для агентов) | `CLAUDE.md`, `.claude/rules/*.md` |
| Карта (как устроено) | `docs/factory/MASTER-PLAN.md` и справочные документы рядом с ним, [`board.md`](board.md) |
| Состояние (что сейчас) | Board, `sites/registry.json` |
| История (почему так) | [`adr/`](adr/), [`CONTRACT-CHANGES.md`](CONTRACT-CHANGES.md) |
| Как работать | эта инструкция, [`SOP-new-order.md`](SOP-new-order.md); в Phase 3 добавятся SOP-launch, SOP-incident, SOP-handoff |

У каждого факта один документ-владелец. Если факт меняется, правится только он; документы — это доказательства, которые сверяются с кодом, а не наоборот.
