# Site types the factory must support

Status: research synthesis, revision 2 (2026-10-06). Revision 1 was reviewed the same day; this revision resolves every blocker and major issue from that review and the minor ones, keeps the section structure, and marks with **Decision** the places where it departs from the reviewer's proposed fix or from revision 1. Written for the owner of a small studio that builds PPC landing sites in bulk and runs Google Ads for them. Covers the three order types the studio actually receives: UK free-to-play **social casino** sites (the finished reference is `/home/user/1/opalquestlounge`, brief `/home/user/1/prompts/social-casino-uk.md`), **online games** sites (browser-game portals and single-game pages) and **hotel-casino** marketing sites (hotels and resorts that have a casino, advertised as hospitality).

## How to read the citations

**No cited official page has been opened by anyone on this project, including during this revision.** The sandbox's egress proxy refuses CONNECT to `support.google.com`, `developers.google.com`, `asa.org.uk`, `cap.org.uk`, `gamblingcommission.gov.uk`, `legislation.gov.uk`, `ico.org.uk`, `schema.org`, `web.dev`, `w3.org` and every example site. Re-tested on 2026-10-06 while preparing this revision: `curl` through the proxy returns no HTTP status for any of those hosts (the proxy log records "gateway answered 403 to CONNECT (policy denial)"), the WebFetch tool returns `getaddrinfo ENOTFOUND` for the same hosts, and the web-search budget shared by this workflow run was already exhausted, so not even new extracts could be gathered. What the project holds for every official URL is a search-engine extract of that URL as read by the first research agent, and nothing else. Only GitHub-hosted material (MDN source, browser-compat-data, schema.org's `schema.ttl`, GameDistribution SDK docs, the Lighthouse changelog) and the local repository were read in full. Revision 1 opened with "Every URL below was opened by a research agent"; that sentence was wrong and is withdrawn.

Rules this revision applies throughout, so that the gap cannot leak into a build gate or a client promise:

1. **Every policy and legal row in section 3 carries a `Verified` value.** `unverified` means: quoted from a search-index extract, never diffed against the live page. Today every row reads `unverified`. A row changes to a date only when the policy-recheck tool (5.5) has opened the live page from a machine with normal egress, stored the page's own "last updated" date and the exact quote, and a named person has initialled the diff.
2. **No quoted policy wording is a failing build gate while it is `unverified`.** A lint or check rule that encodes a quote reads the flag from `types/<type>/policy-urls.json` (shape below) and runs at level `warn` until the entry is verified; a verified entry promotes the rule to its declared level (`error` or `strict`). The only hard gates allowed today are the ones that do not depend on a quote being right: structural and consistency rules of the studio's own making (marked **[factory rule]**), rules that are conservative in every reading (own domain, nothing loaded from a third party before consent, no self-serving review markup), and the two intake rejections in 1.1 and 1.3 that mirror gates the repository already enforces in `build.mjs --strict`.
3. **`policy-urls.json` entry shape** (one file per type pack, read by the lint runner and the recheck tool): `{ "id": "google.social-casino", "url": "https://support.google.com/adspolicy/answer/15132179", "answerId": "15132179", "quote": "<the sentence as this document cites it>", "quotedFrom": "search-index extract, 2026-10-05", "verified": null, "pageUpdated": null, "checkedBy": null, "usedBy": ["sc.no-rmg-brands", "sc.required-statements"] }`. `verified: null` prints as `unverified`; a date promotes every rule in `usedBy`. The same shape, with the territory or helpline payload added, is used by `geo-exclusions.json` and `helplines.json` (5.2).
4. Where the law is involved the document says what the extract of the official page states, flags uncertainty, and marks **lawyer review needed** (LRN). Nothing here is legal advice.
5. The environment can be unblocked by widening Network access in the cloud environment settings (https://code.claude.com/docs/en/cloud-environments#network-access). That remains the first open question in section 7, and it gates the promotion of every rule in section 3.

Marking conventions: **[as indexed]** = quoted or paraphrased from a search-engine extract of the cited URL; **[factory rule]** = the studio's own rule, derived from a policy but not a quote of it, so it carries no policy URL and may be a hard gate; **LRN** = lawyer review needed; **Decision** = where this revision departs from the reviewer's proposed fix or from revision 1, with the reason.

A short glossary used throughout:

- **Engine**: the zero-dependency Node static builder in `opalquestlounge/build.mjs` (856 lines) + `src/lib/layout.mjs` (567), its lint (84 `problems.push` sites in about 40 rule families, free-text messages, no rule ids yet), and the Playwright + axe check suite in `tools/check.mjs` (2,279 lines; 12 named sections over 15 `section()` calls; 136 `expect()`/`pass()` call sites that produce 277 run-time passes because several run in loops; Lighthouse 99-100 confirmed by hand on Lighthouse 12). Counts regenerated with `docs/audit.sh` (5.1).
- **Type pack**: everything that differs between site types (pages, content schemas, components, JSON-LD templates, compliance lint, check sections, chrome, client modules).
- **Site pack**: one client's site: `site.config.json`, content JSON per locale, theme tokens, fonts, media.
- **Mode A / Mode B** (hotel-casino only). **Mode A = a casino-free domain**: no casino reference anywhere on the site (visible text, alt/aria/title attributes, titles and descriptions, OG/Twitter meta, URLs, JSON-LD, media, sitelinks, keywords, ad copy). **Mode B = a casino-referenced site on its own domain** with a casino page, casino offers or casino imagery. **Mode A+** is an explicit intermediate for a client who insists on a neutral amenity mention: it is treated as inside CAP Section 16 and carries the Mode B content, art and age gates site-wide, and it may not target any territory on Google's offline-gambling prohibited list. Revision 1 allowed Mode A to carry "a neutral amenity line"; that contradicted its own CAP citation and is withdrawn (1.3, 3.4).

## 1. Taxonomy

The factory should recognise three top-level types and seven sub-variants. The sub-variant is chosen at order intake because it changes the page set, the compliance matrix and the PPC path. Two sub-variants are now flagged as not advertisable on Google Ads in their current form (`social-casino/demo-lobby`) or only after written confirmations are on file (`hotel-casino` Mode B).

### 1.1 Type `social-casino` (UK free-to-play simulated gambling)

**Definition.** A website offering browser games that simulate casino mechanics (slots, roulette, blackjack) for entertainment only: no real-money stakes, no prizes of money or money's worth, no sweepstakes or redeemable currency.

- Google's Gambling and games policy defines the category as "online simulated gambling-style games where there is no opportunity to win something of value" and allows ads only in listed countries with a dedicated Social casino games certification (https://support.google.com/adspolicy/answer/15132179) **[as indexed]**. Two further sentences of the same policy decide the sub-variants below, both **[as indexed]**: "Ads, sites, or apps must not use logos, names, or marks associated with real-money gambling brands" and "Promotion of content which itself directly promotes engagement in social casino games, such as aggregators or affiliates, is not allowed."
- The Gambling Commission's own position is in its 2015 paper *Virtual currencies, eSports and social casino gaming* (Commission-hosted PDF: https://assets.ctfassets.net/j16ev64qyf6l/4A644HIpG1g2ymq11HdPOT/ca6272c45f1b2874d09eabe39515a527/Virtual-currencies-eSports-and-social-casino-gaming.pdf) read together with Gambling Act 2005 s.6 (https://www.legislation.gov.uk/ukpga/2005/19/section/6), under which gaming means playing a game of chance "for a prize" and a prize means money or money's worth **[as indexed]**. The paper's position, as extracted: winning more credits is not a prize unless the credits are tradeable or can be cashed out, so purchasable but non-cashable chips do not make the game licensable, and the Commission keeps social gaming under review **[as indexed]**. Revision 1 cited this through an Osborne Clarke blog; the primary source replaces it. The "kept under review" caveat and the `purchases: true` path are **LRN** before any purchase or prize-like feature is added.
- On 28 October 2025 Google clarified that sweepstake casinos are not social casino games (https://support.google.com/adspolicy/answer/16641934) **[as indexed]**, so any redeemable-coin mechanic moves the order out of this type entirely.

Sub-variants:

- **`social-casino/own-games`** (advertisable, subject to certification) - the site ships its own HTML5 games (canvas, seeded RNG, virtual currency). This is what `opalquestlounge` is at its core (three house games: `lapidary-wheel`, `brilliant-twenty-one`, `seven-systems`).
- **`social-casino/demo-lobby`** (**non-advertisable**) - the site also embeds third-party provider demos behind a click-to-load stage (the Pragmatic Play demo integration in `src/public/assets/js/games/pragmatic.js`). The repository's `COMPLIANCE.md` section 0(b) rates this mode a launch blocker for Google Ads on two grounds, both quoted above: the real-money brand marks sentence (Pragmatic titles are brands of real-money casino slots) and the aggregators/affiliates sentence; `build.mjs` already warns, and fails `--strict`, when `pragmatic.enabled` and `analytics.adsConversionId` are both set. Revision 1 softened this to "a sub-variant the owner must explicitly accept", citing only the aggregator sentence; that is withdrawn. Rules for this variant:
  - **Intake rejects the variant when any Google Ads account or conversion ID is attached to the order** (mirrors the existing `--strict` gate; hard gate because it does not depend on the quotes being right, only on the owner's recorded decision in `COMPLIANCE.md` 0(b)). The lint `sc.no-rmg-brands` (3.1) is consistent with this: it is expected to fail every demo-lobby page, which is the point.
  - Pragmatic Play's Terms of Use require its "express written consent" for use of the Service "in conjunction with any other games, products, services or software" (`research/policy.md` section 1, **[as indexed]**). A non-empty `pragmatic.writtenConsent` (reference and date) is a **hard intake gate**, not a field to fill later; `build.mjs --strict` already fails on an empty value.
  - **LRN**: trademark use of the game names (Trade Marks Act 1994 s.11(2)(c) honest-practices defence covers naming only, not the game content); and the CAP Section 16 scope test, under which a lobby of real-money branded titles plausibly "implicitly direct[s] the consumer to a play for money gambling product" (3.4).
  - The Commission's social responsibility code 3.2.11 (age verification before free-to-play versions of gambling games) and its July 2019 notice on free-to-play games reached through affiliates bind licensees, and Pragmatic Play (Gibraltar) Ltd is a licensee (`research/policy.md` section 2, **[as indexed]**). They do not bind the studio directly, but they are the reason to expect Pragmatic to require real age assurance before UK consumers reach its demos; the age-assurance decision (self-declaration vs third-party verification, `COMPLIANCE.md` 0(c)) is therefore part of this variant's intake, not an afterthought (3.3).
  - **Decision.** The reviewer offered "define as non-advertisable, or drop the variant". Keep it: the reference build already ships the dual `pragmatic.enabled` mode with its own lint, check builds and compliance text, and a client may legitimately want a demo lobby without Google Ads. It is kept as a variant that the PPC pack refuses, not removed.

Real-world references (reviewed through indexed pages only): the studio's own `opalquestlounge` reference build; a batch of September 2024 ASA rulings against social casino advertisers for implying real money could be won (**verify**: revision 1 named Mobee Co Ltd and Dataverse Co Limited ruling URLs dated 25 September 2024, `research/policy.md` names SpinX Games Ltd A24-1241354 from the same batch; none of the rulings has been opened, so advertiser names, dates and the rules breached are to be recorded in `types/social-casino/docs/rulings.json` when they are); and the Pragmatic Play free-demo host (`demogamesfree.pragmaticplay.net`) used by the lobby variant.

### 1.2 Type `online-games` (free browser games)

**Definition.** A website whose primary content is playable browser games (HTML5) for a general audience, monetised by display advertising, in-game ads carried by a distributor's SDK, or not at all (pure PPC landing for a game brand). No gambling mechanics; any slot/poker/bingo-style free game flips the order into `social-casino`. The decisive legal switch is whether the site is "likely to be accessed by children" under the ICO Children's Code (https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/childrens-information/childrens-code-guidance-and-resources/introduction-to-the-childrens-code) **[as indexed]**. The Data (Use and Access) Act 2025 (c. 18) amends the UK GDPR, the DPA 2018 and PECR; which of its provisions add "children's higher protection matters" and the new PECR exceptions, their section numbers and their commencement dates are **unverified** (revision 1's "section 81" and "5 February 2026" came from extracts and are withdrawn until legislation.gov.uk can be read; 3.3).

Sub-variants:

- **`online-games/portal`** - a catalogue of many games (hundreds to thousands) sourced from distributor feeds (GameDistribution, GamePix, GameMonetize, Playgama, Famobi; Yandex Game Services for CIS; Gamezop for Asia), with category pages, search and related-games rails. Many distributor games carry their own chat, multiplayer lobbies, user names or user-generated levels; the per-game `userToUser` field (2.2) records that, because it changes the Online Safety Act and Children's Code analysis even when the portal itself has no social features (3.3).
- **`online-games/single-game`** - one game (own or licensed) with a landing page, how-to-play, screenshots and optional PWA/offline play; the natural PPC landing for a game brand.
- **`online-games/kids`** - either of the above deliberately aimed at or likely accessed by children; a different consent, analytics and ad-tag configuration (section 3).

Real-world references: Poki (https://poki.com/en/c/faq and https://developers.poki.com/guide/your-game-page: playable frame, plain-language overview, tips, controls, related titles, web-exclusive catalogue so it is not a source of games), CrazyGames (https://www.crazygames.com/game/shellshockersio, a game with in-game chat; quality bar at https://docs.crazygames.com/requirements/quality/ and https://docs.crazygames.com/requirements/technical: rating based on last six months, Released/Updated dates, classification breadcrumb, how to play, FAQ, gameplay video), Coolmath Games (https://www.coolmathgames.com/blog and https://developers.coolmathgames.com/: published curation policy, walkthrough blog), plus Lagged (https://lagged.com/), Y8 (https://www.y8.com/newsroom/y8_updates_game_categories), Armor Games, itch.io's "maximized" click-to-play mode (https://itch.io/updates/more-embed-options-for-html5-games) and Google's GameSnacks load budget (https://techcrunch.com/?p=1945992). All **[as indexed]**.

### 1.3 Type `hotel-casino` (hospitality marketing for hotels/resorts that have a casino)

**Definition.** A marketing or landing site for a hotel, resort or resort group whose amenities include a licensed land-based casino. The site sells rooms, dining, shows, spa, offers and location, with a booking call to action that hands off to the client's booking engine or an OTA affiliate link.

The two policy facts that shape the type, both **[as indexed]** and both to be verified on the live page before any rule built on them is promoted:

- Google Ads classes promotion of "legal physical, real-world gambling activity or establishments" (brick-and-mortar casinos, and Google's own example "entertainment events at casinos") as **offline gambling**, prohibited in a list of about 35 territories (https://support.google.com/adspolicy/answer/15132179, https://support.google.com/adspolicy/answer/16703175). The territory list is data (`types/hotel-casino/geo-exclusions.json`, 3.1), not prose in this document.
- CAP advice says an ad for "a hotel complex that includes a casino" becomes subject to CAP Code Section 16 as soon as the casino is listed among the amenities (https://www.asa.org.uk/advice-online/betting-and-gaming-licensed-casinos-and-non-gaming-facilities.html). The ASA's remit has covered marketing content on advertisers' own websites since its 2011 digital remit extension (**[as indexed]**, remit pages in 3.4), so the landing page's own amenity line is itself a marketing communication under that advice.

Those two facts, read together, force the mode definitions in the glossary and the following rules:

- **Mode A is a casino-free domain.** Nothing on the site, in the ads, keywords, images, sitelinks or JSON-LD refers to the casino. Intake rule: a Mode A build has no `casino` entity, no `containsPlace: Casino`, no `amenityFeature` naming a casino, no casino media on the domain, and no event whose venue is casino-linked (next bullet). Lint `hotel.mode-a-no-casino-terms` runs over the whole build (every page's visible text, attributes, meta, JSON-LD and paths; 5.4 defines `casinoRef(page)`), not only over ad copy, keywords and the landing path as revision 1 had it. **Decision.** The reviewer scoped the "no casino reference anywhere" rule to UK-targeted and prohibited-geo campaigns. It is applied to every Mode A build instead: once Mode A and Mode B live on separate domains (next bullet) a casino-free Mode A domain costs nothing extra, the lint has one definition, and a Mode A domain can then be pointed at any market without re-auditing it.
- **Mode A and Mode B are separate domains, and preferably separate Google Ads accounts.** Google reviews the destination, not only the ad path; a Mode A campaign that targets a prohibited territory while the same domain hosts `/casino/` pages points at a site that promotes a brick-and-mortar casino, and "the ad never mentioned the casino" is not a defence the policy text (as extracted) offers; a disapproval in one campaign can escalate to account-level enforcement. Revision 1 mentioned separate domains only as a commercial (remarketing) reason and said a resort group could run both modes "from the same content"; that is withdrawn. A single domain serving both modes is a policy risk, not a configuration option, whenever any target market is on the prohibited list or Mode A relies on remarketing, which for a PPC landing site is nearly always; so separate domains are the default for every Mode A/B pair until a written answer from Google's policy team says otherwise (7 Q5).
- **Mode A+ (amenity mention)** exists only for a client who insists; it is defined as inside Section 16 in full (16.3 content rules, 16.3.12 strong-appeal art rules, 16.3.14 under-25s, social-responsibility rules) for the entire site, cannot target prohibited territories, and is **LRN** before the first order. The CAP advice quote must be verified on the live page before this mode is offered at all.
- **Events: `casinoEvent` is derived, never typed by an author.** Google's own example of offline gambling is "entertainment events at casinos", so a show in the resort's casino theatre is one even when the word "casino" is absent from the offer. `event.venue` references a `venue` record; a venue is casino-linked when it is the casino itself, a casino-branded theatre/showroom/lounge, or physically inside the casino (`venue.casinoLinked: true`, set at intake from the property map). Any event whose venue is casino-linked forces Mode B; in a Mode A build the lint fails on it. Events in a hotel venue that merely shares a building with the casino are marked **verify with Google policy team** (7 Q5) and default to Mode B until answered.

Sub-variants:

- **`hotel-casino/single-hotel`** - one property, one address, one booking engine. Example: Hilton Batumi (https://www.hilton.com/en/hotels/busbthi-hilton-batumi/), Genting Hotel at Resorts World Birmingham (https://www.resortsworldbirmingham.co.uk/offers).
- **`hotel-casino/integrated-resort`** - one property with many venues (casino floor, several restaurants, theatre, pool complex, meetings), many offer mechanics, often multilingual. Examples: Wynn Las Vegas (https://www.wynnlasvegas.com/rooms-and-suites, https://www.wynnlasvegas.com/offers), Marina Bay Sands (https://www.marinabaysands.com/hotel/packages.html), City of Dreams Mediterranean, Cyprus (https://www.cityofdreamsmed.com.cy/en/casino, https://www.cityofdreamsmed.com.cy/en/accommodation), Crown Melbourne (https://www.crownmelbourne.com.au/hotels).
- **`hotel-casino/resort-group`** - several properties under one brand with a property picker, per-property pages and a shared loyalty programme. Examples: Monte-Carlo SBM (https://www.montecarlosbm.com/en/hotel-monaco, https://www.montecarlosbm.com/en/offers), Sun International / Sun City (https://www.suninternational.com/sun-city/specials), Resorts World Genting (https://www.rwgenting.com/en/genting-rewards/promotions.html), Caesars (https://www.caesars.com/caesars-palace, https://www.caesars.com/las-vegas/hotels/deals).

Across the three the landing mode is orthogonal to the sub-variant, but it is a property of a domain, not of a campaign: a resort group that wants UAE-targeted hotel campaigns and GB-targeted casino campaigns builds two site packs on two domains from shared source content, with the Mode A pack stripped of every casino entity at build time and linted as such (section 4.3).

### 1.4 Explicitly out of scope (reject at intake)

- Real-money online gambling or any link to it (needs a Gambling Commission remote licence and Google online-gambling certification; also pulls a hotel site into "online gambling-promoting content").
- Sweepstakes/"sweeps coins" casinos (not social casino per https://support.google.com/adspolicy/answer/16641934 **[as indexed]**).
- `social-casino/demo-lobby` with a Google Ads account or conversion ID attached (1.1), and any demo lobby without the provider's written consent on file.
- `hotel-casino` Mode B for a Great Britain target until the Gambling Act 2005 opinion in 3.5 is on file, and Mode B for any target until Google's written confirmation in 6.2 is on file.
- "Like Poki, with their games" portals built by scraping Poki/CrazyGames iframes (both are web-exclusive or sitelocked: https://developers.poki.com/guide/revenue-deal-types, https://docs.crazygames.com/resources/html5/sitelock/ **[as indexed]**).
- Hotel Ads / free booking links as a studio service (needs the hotel's CRS/IBE connectivity partner and Hotel Center: https://developers.google.com/hotels/connectivity-partners **[as indexed]**), unless the owner decides to partner (open question).

## 2. Per-type specification

### 2.0 What all three types share (the engine baseline)

The current engine already provides, generically: CSS partial join + minify, content-hashed fonts, immutable `/assets/v<hash>/` URLs, sitemap/robots/manifest, Cloudflare `_headers` with CSP by hash (no inline style or script, no nonce), a service worker with a derived precache, consent banner first in tab order, JSON-LD `@graph` with `@id` resolution, a lint covering one h1, title/description length, canonical, broken links/anchors/IDREFs, inline-script hash vs CSP, no cross-origin fetch before interaction, OG image presence and size, glyph coverage, typographic apostrophes, first-view (150 KB gzip) and precache (220 KB gzip) budgets, and a Playwright + axe suite at 360/768/1440 px in both themes. Consent Mode v2 is implemented in `src/public/assets/js/lib/consent.js` in "basic" mode: all seven consent signals default denied, `ads_data_redaction: true`, `url_passthrough: false`, and `gtag.js` is not requested until the visitor accepts. In basic mode `wait_for_update` has no effect (there is no tag to wait), so it is not an "add" to the existing setup as revision 1 said; it belongs to the advanced-mode variant that is still an owner decision (4.0, 7 Q10). These are inherited by every type unless the type pack overrides a budget.

Common page set for all types: `/`, `/about/`, `/contact/`, `/privacy/`, `/cookies/`, `/terms/`, `/accessibility/` (statement; a default deliverable on every site, see the EAA note), `404`, and `/offline/` only where the pack enables the service worker (`pack.offline`, 5.3).

EAA note: the European Accessibility Act is Directive (EU) 2019/882 (https://eur-lex.europa.eu/eli/dir/2019/882/oj, not opened), applicable from 28 June 2025 **[as indexed]** through national transposition laws. Whether a pure marketing site that hands booking to another host is an "e-commerce service" in scope, who the obligated service provider is (the hotel, not the studio), and whether the microenterprise exemption applies are per-client lawyer questions (**LRN**); UK-only sites are outside the EAA. Revision 1 cited two blogs (accessibility-developer-guide.com, prostay.com) for "mandatory"; those are replaced by the Directive reference plus a national transposition page to be opened per market. The statement stays a default deliverable because it is cheap and harmless.

Each additional country needs its own certification **[as indexed]**.

**Performance budget**: first view 150 KB gzip (HTML+CSS+JS), precache 220 KB gzip, Lighthouse 99-100, no third-party request before interaction and consent.

**Accessibility notes**: WCAG 2.2 AA via axe; keyboard-playable canvas games with aria-live announcements; dialogs follow the APG modal pattern; reduced-motion respected.

- **`engine/client/track.js` (new; replaces `track()` in `consent.js`).** Today `consent.js` sends `ad_personalization: 'denied'` unconditionally on every update, so no Google Ads remarketing audience can ever be built on any site, and `track()` fires only when `current.analytics && loaded`, so a visitor who accepts "Advertising measurement" but rejects "Analytics" produces no Ads conversion at all; there is no `gtag('event','conversion',{send_to})` path, no `event_callback`/timeout before navigation for outbound `book_click`/`call_click`, and no linker configuration. `track.js` has two gates: analytics events need `analytics_storage` granted; Ads conversions need `ad_storage` + `ad_user_data` granted; `ad_personalization` is granted only when `site.config.analytics.personalisation` is true, which the hotel Mode B and social-casino packs force to `false` (3.1 precautionary default). `conversion(name)` reads `analytics.conversions[name]` from `config.js`, sends `gtag('event','conversion',{send_to, value, currency, transaction_id, event_callback})` and navigates after the callback or a 300 ms timeout; `gtag('config', ga4, {linker: {domains: analytics.crossDomain}})` is set from config. The `consent` check section asserts the events delivered in all four states (none / analytics only / ads only / both). **Decision.** The reviewer's gates describe basic mode, which is what ships. If the owner later chooses advanced mode (Q10), gtag loads with denied defaults and applies the consent signals itself (cookieless pings, modelled conversions); the Ads gate in `track.js` then becomes a pass-through for `conversion()` and only the analytics gate stays client-side.
- **Consent Mode v2**: defaults denied for `ad_storage`, `ad_user_data`, `ad_personalization`, `analytics_storage` (plus the three functionality signals), `ads_data_redaction: true`, `url_passthrough: false`, update from the banner; required for EEA/UK since 6 March 2024 (https://developers.google.com/tag-platform/devguides/consent **[as indexed]**). Owner decision pending (Q10): basic mode (current: no Google script until consent, fewer modelled conversions) vs advanced mode (gtag loads with denied defaults, cookieless pings; this is the variant where `wait_for_update: 500` belongs; basic mode needs nothing). **LRN** under PECR.
- **GTM**: opt-in only. Google's own CSP guidance for Tag Manager wants a per-response nonce or `'unsafe-inline'` (https://developers.google.com/tag-platform/security/guides/csp **[as indexed]**), which conflicts with the engine's hash-based static CSP. If used: "Consent Initialization - All Pages" trigger for the consent defaults tag (https://support.google.com/tagmanager/answer/10718549), Google tag on Initialization, Conversion Linker with cross-domain on (https://support.google.com/tagmanager/answer/7549390), per-event Ads conversion tags with built-in consent checks. One container per client, never shared (related-accounts rule, 3.1).
- **GA4**: key events imported into Google Ads as secondary/observe-only, Google-Ads-native tags as primary (https://support.google.com/google-ads/answer/13735417, https://support.google.com/google-ads/answer/2375435); cross-domain measurement when a booking engine or games origin is on another host (https://support.google.com/analytics/answer/10071811). One property per client. All **[as indexed]**.
- **Auto-tagging on** for every account; gclid wins over UTM in GA4 (https://support.google.com/analytics/answer/10723328 **[as indexed]**). UTMs only for non-Google channels: `utm_source=google|meta|newsletter`, `utm_medium=cpc|paid_social|email`, `utm_campaign=<site>_<type>_<market>_<theme>`, `utm_content=<lp-variant>_<ad-id>`, `utm_id=<campaign id>`. Tracking templates use ValueTrack (`{campaignid}`, `{adgroupid}`, `{creative}`, `{keyword}`, `{matchtype}`, `{device}`, `{loc_physical_ms}`) and must resolve to the same page (destination mismatch rule). The engine ignores unknown query params for caching but passes them to the tag.
- **Landing-page variants**: `/lp/<theme>/a/`, `/lp/<theme>/b/` on the same domain, sharing compliance blocks, `noindex` but crawlable by AdsBot, with a GA4 `lp_variant` parameter; tested through Google Ads Experiments / "Update URL ad variation" (https://support.google.com/google-ads/answer/10682377 **[as indexed]**).

- **Account hygiene (related accounts, 3.1)** **[factory rule]**: one client-owned account per order under the studio MCC with agency authorisation; the client's own payment profile; no GTM container, GA4 property, conversion ID, Google tag, domain, creative set or content template shared between clients; a suspension playbook in the launch checklist (no new account for a suspended business; appeal; freeze sibling launches; record the cause); `factory.cross-site-similarity` run across every site under the MCC before each launch.

How `thirdParties[].loadedBy` and `consent` map to the rest of the engine: `loadedBy: static` = the host may appear in static markup (`<img>`, `<link>`, `<iframe>`) and in the CSP; the "loads from another origin before interaction" lint and `refuseOthers()` allow only these hosts. `loadedBy: consent` = requested by `consent.js` after the visitor grants the entry's `consent` category (gtag.js is the only such entry today). `loadedBy: click` = requested only by an embed adapter after a click **and** a stored choice covering the category (the hard gate, 5.4); the host goes into `frame-src`/`connect-src` but may never appear in static markup. `consent` category = the consent dialog row and cookies-page section the entry generates (`necessary` has no switch), the Consent Mode signal it drives (`analytics` -> `analytics_storage`; `ads` -> `ad_storage` + `ad_user_data`; `embedded` -> no Google signal, gates adapters), and the `v:2` store key. `formAction: true` adds the hosts to CSP `form-action`.

**Per-type content schemas** (`types/<type>/schema/*.json`): generated from the field tables in 2.1-2.3, which are normative for `required`, enums and patterns; one file per entity (`game`, `category`, `provider`, `audience`, `hotel`, `room`, `offer`, `venue`, `event`, `casino`, `gallery`, `location`, `booking`, `review`). Derived fields (`event.casinoEvent`) are rejected when present in content. **Decision.** The reviewer asked for the schema files to ship with this design; the normative content ships here (the skeleton above, the typed field tables, the data-file shapes below), and the JSON files are the first deliverable of migration step 0 because they are generated from these tables rather than written twice.

### 5.4 Generalisations of existing components

- **Embed stage -> click-to-load embed with provider adapters.** Keep the exact design of `ui/stage.mjs` + `games/pragmatic.js` (no iframe in static HTML, idle/loading/ready/failed/blocked, HEAD probe, `securitypolicyviolation` listener, offline guard, aria-live, focus management) and add adapters: `game` (own origin or distributor), `booking` (engine widget), `map` (Maps Embed), `video` (YouTube nocookie). Each adapter declares `{frameHosts, connectHosts, allow, aspect, sandbox, consentCategory, srcBuilder, attribution, orientation, fallback}`; `build.mjs` composes CSP `frame-src`/`connect-src`/`form-action` and the `Permissions-Policy` header from the adapters through `pack.csp()`/`pack.permissions()` (e.g. `fullscreen=(self "https://html5.gamedistribution.com" "https://embed.gamedistribution.com")`, `gamepad`, `accelerometer`/`gyroscope` for tilt games, `screen-wake-lock`; keep `camera`, `microphone`, `geolocation`, `payment`, `usb`, `browsing-topics` at `()`), mirroring the same origins in the iframe `allow` attribute (MDN Permissions-Policy semantics, read from mdn/content). The header addition is optional: `fullscreen` defaults to `self` and the iframe `allow` attribute delegates it, which is why the current fixed header already passes the stage's fullscreen check; the list stays minimal and the lint checks that every iframe `allow=` token is permitted by the header or absent from it.
  - **Consent is a hard gate on every adapter.** Today the frame loads whenever the visitor has not chosen "Reject all": an undecided visitor (banner still showing, or no banner at all because analytics is not configured) gets the frame on the first click with only the figcaption as disclosure (`pragmatic.js` `load()` asks only when `demosRefused()`). The generalised adapters (GameDistribution with its IMA ads, Maps Embed, YouTube) would inherit that. Under the ICO storage-and-access guidance as this document cites it, that is loading without prior consent. New rule: if no valid stored choice covers the adapter's `consentCategory`, the click opens the consent dialog (or an inline "Load and allow cookies" confirm, the pattern `pragmatic.js` already uses after "Reject all") before any request leaves the page. Check "embed never requests its host before a consent decision" joins the generic embed section. **Decision.** Whether a clearly labelled click ("Play demo: this loads from X and may set cookies") can itself be the consent act is the **LRN** item that `COMPLIANCE.md` 0(f) already lists; until a lawyer says yes, the hard gate is the default, and the basic/advanced-mode and category copy are signed off with it.
  - **Sandbox.** Do not sandbox third-party ad-funded games (breaks IMA ad clicks, storage, orientation lock). Sandboxed frames must be **cross-origin**: `allow-scripts` + `allow-same-origin` on a frame from the page's own origin nullifies the sandbox (the frame can remove its own attribute), so own/licensed games live on `games.<brand>` as a hard precondition, with `sandbox="allow-scripts allow-same-origin allow-pointer-lock allow-orientation-lock allow-popups allow-popups-to-escape-sandbox"` (`allow-popups-to-escape-sandbox` does nothing without `allow-popups`; revision 1 omitted the latter); the games origin serves its own `_headers` with `frame-ancestors https://<brand>`; lint `games.sandbox-cross-origin`.
  - Add the "maximized" CSS fallback for iPhone and a rotate overlay; the failed state must say "this game cannot be played here" for sitelocked games rather than implying a network error.
- **Lobby -> catalogue; SVG cover -> media card.** `catalogue(ctx, {items, facets: pack.facets, groups})`; `item.media` is `{svg}` or `{picture: manifestEntry}`; the "lobby filter tags must be real filters" lint becomes "every `data-tags` value is a declared facet". `60-lobby.css` becomes `engine/styles/60-catalogue.css`.
- **RG tools and age gate -> optional module with three levels, and `casinoRef(page)`.** `full` (social casino: clock, reality check, limits, breaks, wallet, 30-day age lock), `info` (hotel-casino Mode A+/B), `off` (online games, hotel Mode A). The detection function shared by lint and checks: `casinoRef(page) = /\bcasino\b/i` (plus the locale dictionary's equivalents, e.g. `казино`, `კაზინო`) over `visibleText(page.html)` + every `alt`/`aria-label`/`title` attribute + the JSON-LD text + `og:*`/`twitter:*` meta + `page.path` + the `<title>`. Rules: **Mode A**: `casinoRef` must be false on every page (`hotel.mode-a-no-casino-terms`, `error`). **Mode A+**: `casinoRef` may be true only through the exact string in `site.config.amenityWhitelist` inside an amenity list item, and never in hero, OG, title, description, URL or JSON-LD (`hotel.mode-a-plus-amenity-only`). **Mode B**: every page where `casinoRef` is true renders `pack.chrome.rgBlock(market)` in initial HTML before the footer (`hotel.rg-block`), with helplines from `types/hotel-casino/helplines.json` keyed by `geo.market` (the target market, not the page locale: a `/ru/` page in a GB-targeted campaign shows GamCare) and `entryAge` from `casino.entryAge`; the optional soft interstitial on `/casino/` is a `<dialog>` reusing the age-gate markup contract (`#age-gate`, `[data-age]`, `aria-busy`), dismissable, stored under `<prefix>.age` with the same 30-day memory as the social-casino gate. `age-boot.js` is generated from config (prefix, threshold 18/21/25) into `OUT/assets/js/` (5.3); the CSP is untouched.
- **Consent categories become data, and the store becomes `v:2`.** Store shape `{v: 2, at, categories: {analytics: bool, ads: bool, embedded: bool, ...}}` with a one-off migration from `v:1` (`demos` -> `embedded`; `analytics`/`ads` carried over; a `v:1` choice older than the migration date is re-asked rather than guessed); the consent dialog rows and the cookies page are generated from `thirdParties[]` grouped by `consent` category (the hand-written rows in `layout.mjs` `dialogs()` go); `demosRefused()` becomes `refused('embedded')`; the `consent` check section reads `categories.*` instead of `analytics === false && demos === false`. This is a schema change in `consent.js`, not a move (5.1).
