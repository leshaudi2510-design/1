# Новый заказ: от брифа до PR на ревью

Пошаговая инструкция для оператора. Общие правила, команды и значения гейтов — в [`SOP-operator.md`](SOP-operator.md). Источник: SPEC 16 (переходы стадий), SITE-TYPES 1.4 и 6 (что принимаем и какие поля нужны), MASTER-PLAN 5.1 и 9.

Пометка **[Phase N]** у шага значит, что по плану этот шаг автоматизируется в фазе N. До этого его делает человек по выводу команды.

## 0. Это новый заказ или правка?

| Что просят | Что делать |
|---|---|
| Новый сайт, новый бренд, новый домен | этот документ, начиная с шага 1 |
| Изменить текст, картинку, игру, исправить ошибку CI на уже начатом или живом сайте | `/fix <slug> "<что сделать>"` **[Phase 3]**; до этого — правка в ветке сайта и `/qa` |
| Сменить тип сайта (например, игровой портал стал социальным казино) | новый заказ: тип меняет набор страниц, правила и рекламный путь |

**Правки, которые всегда смотрит судья по правилам** (`compliance-judge`), даже если они маленькие: любые слова о деньгах, бонусах, возрасте, шансах и выигрышах; любое стороннее встраивание (iframe, скрипт, карта, виджет бронирования); любое изменение юридических страниц.

## 1. Проверить, берём ли заказ

Фабрика **не берёт** (SITE-TYPES 1.4):

- игры на реальные деньги и любые ссылки на них;
- sweepstakes / «sweeps coins» (монеты, которые можно обменять на призы);
- демо-лобби социального казино (`social-casino/demo-lobby`), если к заказу привязан аккаунт Google Ads или conversion ID, и любое демо-лобби без письменного согласия провайдера;
- отель-казино в режиме **B** для Великобритании, пока нет заключения юриста по Gambling Act 2005, и в режиме B для любой страны, пока нет письменного подтверждения Google;
- «как Poki, с их играми» — порталы на чужих iframe с Poki или CrazyGames;
- Hotel Ads / free booking links как услугу студии (пока владелец не решит иначе).

`/order` отклоняет эти случаи сам на уровне `draft`. Если бриф похож на один из них, скажите клиенту сразу.

## 2. Завести заказ

```
/order <путь к брифу или текст брифа> --type <social-casino|online-games|hotel-casino> [--variant <вариант>]
```

- Тип и вариант можно не указывать: `intake-analyst` определит их сам и, если не уверен, спросит вас первым вопросом.
- Варианты: social-casino — `own-games` (свои игры, можно рекламировать после сертификации) или `demo-lobby` (демо провайдера, рекламировать нельзя); online-games — `portal`, `single-game`, `kids`; hotel-casino — `single-hotel`, `integrated-resort`, `resort-group`, плюс режим `casinoMode`: **A** (домен без упоминаний казино, по умолчанию), **A+** (одно нейтральное упоминание, только после юриста), **B** (сайт с казино на своём домене, только после подтверждений).
- Без названия бренда команда остановится: из названия получается `id` заказа.

Что появится:

| Файл | Что внутри |
|---|---|
| `orders/<id>/brief.md` | бриф дословно |
| `orders/<id>/order.json` | заказ; у каждого поля указан источник (`brief`, ответ клиента или `default`) |
| `orders/<id>/questions.md` | вопросы клиенту на его языке, две группы: «до сборки» и «до запуска»; у каждого вопроса строка `field:` |

Стадия становится `questions-sent`. **[Phase 2]** ветка `site/<slug>`, черновой PR и строка заказа на Board создаются автоматически. В Phase 1 Board получает только строки `sites`, `events` и `runs` (D-38), а ветку и PR открывает человек.

Проверка уровня `draft` вручную:

```bash
node tools/validate-order.mjs orders/<id> --level draft --json
```

## 3. Отправить вопросы и влить ответы

1. Отправьте клиенту `questions.md` (письмо, мессенджер — как договорились).
2. Ответы клиента сохраните в файл или вставьте текстом:

```
/order <id> --answers <файл или текст>
```

Ответы вливаются по строкам `field:`, у поля появляется дата ответа, заказ проверяется заново.

Что **клиент обязан дать сам** (фабрика это не придумывает): юрлицо, номер регистрации и реестр; кто владеет аккаунтом Google Ads и чей платёжный профиль; лицензии и номера лицензий (отель-казино); факты об отеле и казино; адреса движка бронирования и партнёрские ID; телефоны; фотографии с правами; письменные согласия провайдеров демо; подписанную оценку аудитории; юридические заключения. Что **фабрика делает сама**: концепцию, все тексты из структурированных фактов, структуру сайта, JSON-LD, юридические страницы из реквизитов, OG-картинки (SITE-TYPES 6.3).

Фабрика **никогда** не выдумывает: рейтинги, отзывы, звёзды отеля, цены «от», PEGI, фразы «licensed by», выигрыши, ссылки на казино на реальные деньги, телефоны горячих линий в тексте (они берутся из таблицы `helplines.json`).

## 4. Оценка аудитории (онлайн-игры и социальное казино)

```
/order <id> --assessment
```

Готовит черновик `orders/<id>/audience-assessment.md` по вопросу «вероятно ли, что сайт будут открывать дети» (ICO Children's Code). Это юридическое решение: фабрика только готовит черновик. Подписывает названный человек (кто — вопрос владельцу №11). Поле `audience` в заказе заполняется только из подписанного файла.

## 5. Предложение клиенту: три направления

Когда отвечены все вопросы «до сборки»:

```
/order <id> --propose
```

- Панель концепций (`concept-panel.js`) делает три направления. Каждое заранее проверено на уникальность против других сайтов того же типа (`uniqueness.mjs --pre`) и оценено судьями.
- Результат: `orders/<id>/proposal.md` с таблицей оценок. Стадия `proposal`.
- Если направление делит семейство концепций с другим сайтом, оно показано с пометкой «shares a concept family with <slug>»: эту пометку надо подтвердить.
- **[Phase 3]** приватная страница предложения для клиента с кнопками «утвердить» по каждому пункту. До этого одобрения вносит оператор на Board со слов клиента (режим relay).

## 6. Одобрения и утверждение

Клиент утверждает по отдельности (набор пунктов зависит от типа, `pack.approvalItems[]`):

- общие: концепция (с выбором направления), палитра, шрифты, структура, тексты, реквизиты оператора, юридические тексты, запуск;
- social-casino: ещё валюта и игры;
- online-games: ещё каталог, политика отбора игр, аудитория;
- hotel-casino: ещё факты об отеле, предложения, фото, бронирование.

Когда утверждены пункты, нужные для сборки:

```
/order <id> --approve
```

Проверка `--level build`, резерв концепции в реестре **[Phase 2]**, проект Cloudflare **[Phase 3]**. Стадия `approved`. **[Phase 4]** это делает рутина `orders-inbox` раз в час сама.

## 7. Сборка

```
/build <slug>
```

- **Phase 1:** сайт создаётся из шаблона типа (`types/<тип>/template-site/`), собирается и проходит часть проверок. Шаблон собирается без ошибок с первой минуты, но в строгом режиме падает на текстах по умолчанию, общих обложках и заглушках — так и задумано: ничего шаблонного не уйдёт в прод.
- **Phase 2:** полный конвейер `build-site.js`: творческие линии в параллель (тексты + рисунки, затем тема + линия типа), сборка, до трёх проходов линта, проверка, документы, PR.
- **Phase 3:** `/batch` раздаёт утверждённые заказы облачным сессиям, по одной на сайт, волнами.

Правила цикла сборки: проверка → правка → проверка не бесконечна. Если раунд не улучшил результат (одна попытка в сессии сайта, две в hub), цикл останавливается и заказ уходит на `fix` или к человеку.

## 8. Проверка

```
/qa <slug>
```

Нужно, чтобы были зелёными G2–G6 (таблица в [`SOP-operator.md`](SOP-operator.md), раздел 5): строгая сборка без проблем, все браузерные проверки, Lighthouse ≥ 95, уникальность. Красный гейт → исправить то, что названо в отчёте, и снова `/qa`.

Типичные причины красного `--strict`:

| Правило | Что значит | Кто чинит |
|---|---|---|
| `default-content` | на странице текст по умолчанию из шаблона | линия текстов |
| `generic-cover` | общая обложка вместо своей | линия рисунков |
| `placeholder` | в реквизитах заглушка `[…]` | клиент: вопрос в `questions.md` |
| `vocabulary-usage` | на странице мало слов из словаря концепции | линия текстов |
| `token-contract` | тема не задала обязательный токен | линия темы |
| запрещённое слово | в тексте слово из запретного списка | переписать текст |

Никогда не чините линт, убирая или ослабляя правило: хук не даст править `engine/**` с ветки сайта.

## 9. Ревью и правки [Phase 3]

- PR с меткой `stage:review` → `/review <slug>`: три скептика по уникальности + судья по правилам + машинные сигналы. Решение: `ready`, `fix` или `blocked`.
- `fix` → `/fix <slug> --from-review=N`: каждое блокирующее замечание — отдельный коммит.
- Не больше трёх раундов. Четвёртый раунд → `blocked` и красное событие.

## 10. Запуск [Phase 3]

Запуск — отдельная инструкция (SOP-launch, появится в Phase 3). Коротко: `/status --gate <slug>` показывает недостающие отметки и команды, которые дают доказательства; клиент одобряет запуск на странице Evidence; вы набираете `ship <slug>` в `/ship`; дальше мерж, деплой с проверкой и откатом, и `pr-shepherd` переводит сайт в `live`.

## Особенности типов в Phase 1

| Тип | Состояние в Phase 1 | Что важно при заказе |
|---|---|---|
| social-casino | полный путь; Opal Quest Lounge — сайт №1 | ≥ 3 своих игр в любом режиме; дисклеймер дословно; 18+; GamCare 0808 8020 133 и NHS; демо Pragmatic только с письменным согласием и без Google Ads |
| online-games | заготовка (stub): шаблон собирается с предупреждением `type-stub`; полный пакет — Phase 4 | вариант, провайдеры и их разрешение на платный трафик, аудитория (подписанная оценка) |
| hotel-casino | заготовка (stub); полный пакет — Phase 4 | режим A/A+/B (A по умолчанию; A и B никогда не на одном домене), языки, факты об отеле, бронирование |

Пока тип — заготовка, заказ этого типа можно завести и задать вопросы. У заготовки ещё нет обязательных правил типа (`mandatory.pageLints` пуст), поэтому первый настоящий заказ online-games и hotel-casino по плану собирается в Phase 4, вместе с полным пакетом типа (MASTER-PLAN 9.4).
